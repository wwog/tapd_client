# 新缺陷通知（M6）

通知完全由客户端自绘窗口实现，不使用 macOS 系统通知。轮询、分类、去重与处理动作都在桌面客户端内完成。

## 1. 通知范围

设置 → 新缺陷通知：

| 设置 | 说明 |
| --- | --- |
| 总开关 | 关闭后停止轮询与弹窗，已有待处理通知仍保留 |
| 范围 | `我的`（只通知处理人是我）或 `项目`（项目内所有新缺陷） |
| 纯新建 | 新创建且进入范围的缺陷 |
| 转移过来的 | 不是新建，但处理人变成我（优先依据 `assigned_time` 与 `created` 差异；字段缺失时保守判断） |
| 重新打开 | 状态从其它值变为“重新打开” |
| 轮询间隔 | 默认 30 秒，范围 20–600 秒 |
| 免打扰 | 例如 22:00–09:00，期间只累计不弹窗 |
| 最大展示数 | 同时展示的卡片数，默认 3 |

**每次启动或重新登录后，每个项目的第一轮只建立 baseline（只记录状态，不弹通知）**；此后才通知新出现、转派或重新打开的缺陷。因此“进入应用就看到一堆历史通知”不会发生，关闭期间产生的变化也会被首轮静默吸收。未读完的截断轮次不会标记完成，下一轮继续静默补齐后才开始通知。

客户端自己写入的处理人变更（列表 / 详情「认领」、通知卡「处理」自动改派给自己、下拉选择自己）不算转派：写入成功后登记一次性抑制，下一轮轮询只更新 seen，不弹卡片；其他人发起的改派仍会通知。

缺陷列表的每次刷新（手动刷新、30 秒自动刷新、翻页与筛选切换）在列表处于前台且主窗口有焦点时，也会把当前页写入 seen：它等同于一次静默轮询，屏幕里已经看到的缺陷不会在下一轮补发通知。窗口失焦时的自动刷新不算观察（用户可能在别的应用里），仍然正常通知；只更新 seen，不推进轮询 cursor。

轮询范围：`我的` 会跨所有可访问项目增量轮询，每个项目独立维护 cursor（cursor 缺失即首轮 baseline）；`项目` 仍只轮询“上次选择的项目”（`lastWorkspaceId`），避免一个繁忙项目把队列刷爆。

## 2. 通知窗口

- 位置：屏幕顶部居中的常驻胶囊（不占 Dock、始终置顶），可拖动并记住位置。
- 有通知时胶囊展开为 384px 宽卡片；无通知时收起成状态胶囊。
- Agent 运行中 / 待审核，或外部 AI 正在处理缺陷时，鼠标悬停胶囊会在下方展开一张 300px 摘要卡（项目、缺陷 ID、标题与运行状态；外部 AI 还显示客户端与模型），移开鼠标即收起；展开的通知卡片优先，悬停摘要不会覆盖它们。
- 卡片为深色实底、无阴影；标题保留两行，额外卡片向上/向下按可用空间扩展。
- 每条包含：项目、严重程度/优先级、标题、创建人、时间。
- 三个按钮：
  - **处理**：见下一节。
  - **查看缺陷**：聚焦主窗口并打开该缺陷详情（通过 `notification://open-bug`）。
  - **忽略**：标记 ignored，同一缺陷后续不再提示；若之后重新打开可再次通知。

外部 AI 占用期间，胶囊展开后额外显示一张外部 AI 卡片（客户端 · 模型、项目、缺陷 ID 与标题），同样提供「查看缺陷」；右上角可取消占用。

设置页提供「模拟通知」，可在不等待真实新 bug 的情况下验收窗口与按钮（模拟项不能执行处理，也不会跨重启保留）。

## 3. 处理动作

点击「处理」后，客户端会：

1. 读取当前登录用户（缺失时从 TAPD 获取并写回配置）。
2. 拉取缺陷详情，确认当前处理人与状态。
3. 若处理人不是我，调用 TAPD 内部接口改派：
   `POST /api/entity/bugs/inline_update`，字段 `current_owner`。
4. 若状态是起始状态（`new` / `open` / `reopened`），读取该缺陷的工作流（`get_bug_transition_info`），选择工作流允许的“处理中”目标（`in_progress` / `progressing`）再流转：
   - 与详情页状态流转共用 `bug_write::perform_transition` 的端点回退（kanban → workflow），不再盲试所有组合。
   - 工作流没有处理中节点或当前已不是起始状态时只改派，不流转。
5. 全部成功后标记 handled，并：
   - 触发 M7 入队事件 `agent://enqueue`；
   - 刷新主界面缺陷列表；
   - 更新通知窗口。

任一写入失败时不会标记 handled，也不会入队，通知保持可重试；界面会显示失败原因。改派成功但流转失败时，重试会跳过改派、只重试流转。

> 写接口使用的是网页会话 Cookie + `dsc-token`，与 TAPD 网页端同一权限。客户端不会绕过权限。

## 4. 持久化与重置

- 唯一存储：`<数据目录>/cache.sqlite3` 中的 `notification_*` 表（设置、通知条目、seen 去重、ignored、每个项目的游标）。`baseline_done` 表已移除：cursor 缺失即首轮。
- 轮询只增量写入发生变化的行，不再每轮重写整份状态。
- seen 表按 `lastSeen` 保留 90 天，并限制最多 20000 条；被裁剪的 seen 会连同对应的 ignored 一起删除。
- **每次启动会清空上一会话的通知条目**（保留设置、seen 与游标），因此卡片不会跨重启堆积；每个项目首轮静默建 baseline。
- **登录 / 退出登录 / 会话过期会清空条目、seen、ignored 与游标**（保留设置），换账号不会继承上一个账号的去重状态。
- 重置本地数据会删除整个数据目录（含数据库）；下次启动重新建立 baseline，不会触发历史通知。
- AI / MCP 通知只存在于内存，不写 SQLite，也不会跨重启保留。

## 5. 已读 / 未读

TAPD 的缺陷接口没有暴露“通知已读/未读”状态，客户端**不自行发明未读数**，因此：

- 不做托盘角标 / 未读计数；顶部胶囊只展示当前 pending 的通知与 Agent 状态。
- 不提供通知历史视图；本地状态 `pending / handled / viewed / ignored` 表示“用户对这条通知做了什么”，不是 TAPD 的已读状态。
- 若后续 TAPD 暴露已读接口，再接入真实未读数。

## 6. AI / MCP 通知

除了 TAPD 缺陷轮询，AI 客户端（opencode、Claude Code、Cursor、Codex、ZCode 等）也可以通过 MCP 工具在同一个胶囊里提示用户。它与缺陷通知共用窗口和展开动画，但使用独立的通用卡片：

- 入口：`tapd_notify_user`（唤起并等待用户操作）、`tapd_wait_notification`（继续等待）。
- 卡片格式：`tone`（info / success / warning / error / progress）+ 标题 + 内容块（text / code / fields / progress / divider）+ 最多 4 个动作按钮。
- 用户点击按钮或关闭后，结果作为同一次 MCP 工具调用的返回值交给 AI（`acted` + `actionId` / `dismissed` / `timeout` / `replaced` / `expired`）。
- `tag` 相同的待处理通知会被替换，适合进度类连续更新，不会堆满胶囊。
- AI 通知不受免打扰时段限制（它是用户主动要求的提示），但可以在设置里关闭「允许 AI / MCP 唤起通知」。
- 设置页提供「调试通知」：选择配色、编辑标题/正文、勾选带「确认 / 取消」按钮，发送后可看到最近几条卡片及其回执，用来验证格式与反馈链路。

## 7. 已知限制

- `assigned_time` 依赖 TAPD 列表/详情返回；若项目不返回该字段，“转移”判定会保守，可能漏报或归类为新建。
- 项目范围会对首次出现的候选缺陷额外拉一次详情，请求量高于“我的”范围。
- 通知卡片不支持拖拽排序/分组；一次最多展示 `maxVisible` 条，其余保留 pending。
- 「我的」范围跨项目轮询会随项目数增加请求量（每项目每轮至少一次列表请求，数据量大时最多 10 页，默认 30s 一轮）。
- 每轮最多翻 10 页（增量）/ 25 页（首次 baseline），单页 200 条，页间有短暂节流。达到上限仍未读完时保留旧 cursor，避免越过未读窗口；极端超量（单窗口 >2000 条改动）时会在同一窗口重复拉取前 N 页，直到数据量回落到上限内。
- 处理动作只做“改派 + 接受”两步；需要补充其它字段的强制流转会被 TAPD 拒绝并显示错误。
