# 工程口味

原则优先于规则。冲突时按此排序：**人能读懂 > 最小改动 > 先跑通再扩展**。项目有自己的规范时，以项目为准。

## 先判断

- 有没有设计/契约？没有就做最小闭环，不补想象需求。
- 先读现有实现和调用点，再决定改哪里；不要凭文件名猜结构。
- 改动半径多大？只动必要文件，不越阶段。
- 真的需要新抽象、配置或兼容层吗？默认不要；至少两个真实调用点才提炼，名字要能让没读过实现的人猜到职责。
- 同一个判断是否出现第二次？出现第二次就上移成构造约束；一行能解决的重复，不写十行。
- 同一事实是否只有一个来源？信息、状态、工具清单、配置项都只维护一份，其他地方引用它。

## 架构

- 目标是**减缓熵增**，不是套模式。新功能应落在确定的层和边界里，而不是靠分支、配置、兜底吸收。
- OS（kernel/process/PID/调度/IPC/HAL）是最好用的参照系之一，hexagonal、actor、event-driven、pipeline 同样按场景选。标准是人能定位、能修。
- 分层网关收口凭证、传输、策略；业务层只留少量纯逻辑，短到一眼看完。
- 依赖单向：核心不依赖框架，同步核心不掺 async/IO 策略。
- **单一职责**：一个 impl/文件同时管调度、持久化、IO、格式转换、平台适配，就是分层失败；按职责拆，让每个单元一屏能讲清。
- 接口级隔离：全局/会话、读/写用不同入口或类型，不用 `scope` 参数在运行时分支。
- 跨平台：核心 sans-IO，文件/网络/时钟/线程/平台 API 都走端口与适配器；公开 API 不出现平台类型；未支持平台可编译、运行时报错。路径、配置、时钟由调用方传入，核心不读环境变量、不猜目录。

### 架构 review 顺序

1. 状态机：每个状态谁写、谁转、终态是否防回退、取消走哪条路。
2. 并发：锁的顺序、check-then-act、async 里的阻塞调用。
3. 失败：哪些被吞、哪些降级不可见、失败后数据是否半写。

## 代码写法

- 命名用业务语言，除开结构不用 `data` / `info` / `handle` / `manager` 这类空词。
- 函数一屏；嵌套超过三层就拆；一个函数只做一件事。
- 注释解释「为什么」，不解释「是什么」；过时注释直接删。
- 同一段逻辑第二次出现就提取，不要复制后各自演化。

## 状态、并发与持久化

- 状态有明确 owner。每个状态/字段/命令都要有生产写入点；没有写入点、没人读的，删掉，不要留成「看起来在生效」。
- 同一个状态只有一个迁移入口；终态防回退，迟到的完成/失败/取消不能把终态改回去。
- 取消、超时、审核是独立路径，不能共用正常完成的一半逻辑；该 stash/暂停/唤醒的步骤不能漏。
- 同一事实的**判定与写入必须在同一临界区**；先查 A 锁再写 B 锁的 check-then-act 视为竞态。
- **异步边界**：async 路径里不跑阻塞 IO、CPU 密集计算、git/文件/系统调用；需要时用 `spawn_blocking` 或独立线程池。同步核心由 async 适配层调用，核心本身不知道 async。
- 增长型状态进数据库并增量写（O(changed)），配置才留 JSON。
- 重启恢复与正常路径共用同一套迁移；恢复必须幂等，重复执行不产生第二份状态。
- 关键副作用失败必须可见：持久化、写库、提交、回写失败不能 warn 后当成功；宁可失败上报，也不静默降级。

## 数据与迁移

- **默认不迁移**：旧格式不自动读取、不自动转换，启动时不做静默导入。
- 迁移/导入是**用户显式触发的动作**，不是运行时路径；没有确认就不碰旧数据。
- 新旧只留一个事实源：要么继续读旧格式，要么一次性导入新格式；不长期双读、双写。
- 迁移单向、可重复执行、旧数据只读；失败就停下报告，不带着半份数据继续跑。
- 不维护多级自动升级链；确实要升级时，每一步写成显式版本迁移，并给出验收标准。

## 崩溃与错误

- **不变量由构造保证，不逐处检查。** 初始化边界校验一次，下游直接拿引用；拿不到就是没初始化，属于程序员错误，不是业务分支。
- 误用/不变量破坏 → 唯一收口点 panic，诊断写清缺什么、该先做什么；数据/环境错误 → `Result`；可预期业务失败 → 领域错误。
- 错误只抽象大类，平台错误码进日志，不进公开接口。
- 崩溃限制在任务，由 supervisor 或进程边界接住；不在全局循环、共享调度器、持锁路径 panic。
- 网络超时、IO 失败绝不 panic。
- 崩溃语义若影响用户可见行为、数据或跨模块契约，先问 wwog，不自行定策略。


## UI

- 默认最小信息：一个事实只出现一次，能从上下文看出的状态不再重复；同一动作只留一个主入口。
- 解释默认收进 `title`；页面通常只留标题；空态一句标题，操作指引进 `title`。
- 只保留动态数据（版本、路径、数量、时间）与破坏性操作警告；其余说明默认不显示。
- 新增元素先问：是否重复了附近信息？删掉会损失什么？**长期不脏**优先。
- **占位符不是数据**：加载中、失败、空是三种真实状态，不用 `"—"`、「已登录」之类兜底冒充内容。
- **装饰要有来源**：不从别的页面搬光斑/插画/边框；没有信息作用的视觉元素删掉。
- 交互跟平台惯例与项目设计系统；像素、阴影、字重等规则归项目规范。
- 成功后界面已有可见结果就不提示；错误必须保留；设置与布局要持久化。

## 测试

- 测契约、具体业务行为、边界、回归；不追覆盖率。一个测试一个行为，用业务语言命名。
- 一个 bug 配一条回归；用真实脱敏数据；不测私有实现。
- 状态机、并发、取消、失败路径优先于 UI 细节；一条足够，不铺开。
- 验证给命令和结果；UI 改动看真实渲染；没覆盖的路径明确写出来。

## 交付

- 大改先给计划，确认再写；只做被要求的那一阶段。计划里写清「不做什么」和残留风险。
- review 给 `file:line`、阻塞项与验证证据，按 P0（数据/并发/契约）、P1（可维护性）、P2（风格）排序。
- **问题不要阻断计划**：先给结论和默认建议；只有影响产品语义/数据/契约的才提问，最多 1 个；其余写成「默认按 X 处理，可否决」。
- 不接管并行会话的半成品，只修阻塞自己的回归。
